0.8.0 builds AppImages. A Linux target that already produces a DEB and an RPM can add one line and also ship a single file that runs without installation.

## New

- **Build an AppImage from the files you already package.** Add `appimage` to a Linux binary target's `formats`. It uses the same `contents` as the DEB and RPM, takes the program to run and the icon from the package's desktop entry, and writes `NAME-VERSION-ARCH.AppImage`. There is nothing else to configure. By @crmne.
- **No `appimagetool`, no nFPM, no running the binary.** The files are packed with `mksquashfs` and appended to a pinned AppImage runtime (type2-runtime 20251108) that is downloaded once and checked against a built-in SHA-256. The same inputs give the same bytes, and an ARM64 AppImage builds on an x86 host. `amd64`, `arm64`, `386` and `arm7` are supported. By @crmne.
- **The reusable workflow is ready for it.** `package.yml` installs `squashfs-tools`, so adding the format needs no workflow change beyond moving to this release. Prereleases may use the format too. By @crmne.
- **Publish Homebrew recipes with a deploy key.** `HOMEBREW_TAP_SSH_KEY` holds a key that can write to the tap alone, as an alternative to a token. The tap is cloned and pushed over SSH, checked against GitHub's published host keys. By @crmne.

```yaml
linux-amd64:
  platform: linux
  arch: amd64
  libc: glibc
  formats: [deb, rpm, appimage]
```

Read [Supported platforms](https://native-packages.dev/platforms/#appimage) for what the package must contain.

## Known limitations

- Libraries are not bundled. The AppImage uses the host's libraries, as the DEB and RPM do, so it runs where your binary's glibc floor and linked libraries are met, not on every Linux system. `build.json` lists those libraries.
- The AppImage carries no update information and is not signed.
- Running an AppImage needs FUSE, or `--appimage-extract-and-run`.
- The format was run on x86_64. The ARM64, i686 and armhf runtimes are pinned and checked, but AppImages for them were not run.
